## 배경 (Mac)

사용자가 "지금 윈도우가 Mac의 포모도로를 따라가고 있지 않다"고 신고해서 실측
조사했습니다. 겸사겸사 "이런 일에 API를 적게 쓰도록 재활용하는 시스템"도 만들어달라고
하셔서 같이 작업했습니다.

## 1. "안 따라감"의 실제 원인 — 버그 아니라 레이스 컨디션

로그로 정확히 재현했습니다:
- Mac: 13:19:17에 로컬에서 focus 세션 시작.
- Windows: **13:29:38**(약 10분 뒤)에 **자기도 독립적으로** focus 세션 시작.

Mac의 "먼저 시작한 세션이 이긴다" 규칙(`candidateWins()`/`acceptIncoming()`)이 정확히
설계대로 동작해서, Mac의 더 이른 세션이 계속 이기고 Windows의 늦은 push는 계속
거부됐습니다 — 이건 버그가 아니라 의도한 보호 장치입니다(다른 기기의 stale idle
스냅샷이 실행 중인 세션을 덮어쓰지 못하게 막는 것과 같은 규칙).

**진짜 원인은 "두 기기가 서로 몰래 각자 세션을 시작한 것"입니다.** Mac은 부팅
시("규칙 1") 항상 pull을 먼저 하고 나서 필요하면 로컬 세션을 시작하는데, Windows의
자동시작(presence-detection autoStart로 추정)이 **로컬에서 세션을 시작하기 직전에
원격 상태를 먼저 확인하는지** 확인 부탁드립니다 — 확인 안 하고 있다면, "이미 Mac이
집중 중"인 상황에서도 Windows가 자기 판단만으로 새 세션을 켜버릴 수 있어서 이런
충돌이 재현될 수 있습니다.

**임시 해결**: 지금 당장은 둘 중 나중에 시작한 쪽(이 경우 Windows)에서 세션을
정지했다가 다시 시작하면(또는 그냥 기다렸다가 다음 자연스러운 idle 전환에서)
Mac의 세션을 정상적으로 받아들이게 됩니다.

## 2. API 호출 줄이는 시스템 — Mac에 구현 완료

서버(`server/pomodoro-api.js`)에 이미 SSE `/stream` 엔드포인트가 있었고 Windows는
이미 이걸로 실시간 push를 받고 있었는데(2026-07-28 실측 확인 기록 있음), **정작
Mac 자신은 이 스트림을 한 번도 안 쓰고 있었습니다** — 45초마다 `GET /state`를 계속
찔러서 확인하는 순수 폴링 방식이었습니다.

**고침** (`main/main.js`, `startApiStream()`):
- 앱 시작 시 `/stream`에 연결해서 계속 열어두고, 서버가 상태 바뀔 때 보내는
  `data: {...}` 이벤트를 그대로 기존 pull 파이프라인(`normalizeApiState` →
  `applyFetchedRemote`)에 흘려보냅니다 — 폴링으로 받던 것과 완전히 같은 처리 경로,
  채널 라벨만 `api-stream`으로 구분.
- 연결 끊기면 1초→2초→4초...30초 상한까지 백오프하며 재연결.
- **45초 안전망 폴링은 스트림이 살아있는 동안엔 API 쪽 GET을 건너뜁니다** — 완전히
  없애진 않고, 스트림이 끊겨 있을 때만 안전망으로 동작(스트림 재연결 로직 자체가
  조용히 죽는 엣지케이스 대비). 파일 채널(공유폴더) 폴링은 스트림 대상이 아니라서
  그대로 유지됩니다.

실측 확인: 재빌드 후 로그에 `[sync-stream] connected` 찍히고, 이후 상태 변화가
`channel:"api-stream"`으로 실시간 반영되는 것 확인. 이제 정상 상태에선 Mac이 API
서버에 반복 폴링 요청을 거의 안 보냅니다.

**Windows 쪽에 제안**: 이미 `/stream`을 쓰고 계시다면 이 부분은 참고만 하시면
되고, 혹시 Windows도 폴링+스트림을 병행하고 있다면 Mac처럼 "스트림 연결 중엔 폴링
건너뛰기"를 넣으면 양쪽 다 API 호출이 더 줄어들 것 같습니다.

## 부탁드리는 것

1. Windows의 자동시작 로직이 로컬 세션을 켜기 전에 원격 상태를 먼저 확인하는지
   점검 부탁드려요 — 위 레이스의 근본 원인일 가능성이 높습니다.
2. (선택) Windows도 폴링을 스트림 연결 상태에 따라 건너뛰는 최적화를 적용할지
   검토해주세요.
