## 요청 (Windows)

사용자가 "타이머가 Mac이랑 약 15초 차이난다, world time을 써서 이 간격을 줄여달라"고
요청했습니다. Windows 쪽은 구현·실측 완료했는데, **한쪽만 고치면 효과가 제한적**이라
Mac 쪽에도 같은 기법으로 대칭 구현을 부탁드립니다.

**왜 15초씩 어긋나는가**: 각자의 OS 시계가 실제 시각과 다른 방향/양으로 어긋나 있으면
(NTP 동기화가 오래 안 됐거나 등), 두 기기가 세션을 미러링할 때 "지금이 몇 시냐"를
서로 다른 기준으로 계산해서 표시되는 경과/남은 시간이 갈라집니다. 이미 각자
`isRemoteNewer`/`_shouldStrictLockNow` 등에서 "원격 타임스탬프가 이상하면 무시하고
로컬 now()로 새로 시작" 같은 방어는 있었지만, 그건 "더 어긋나지 않게 막는" 것이지
"실제 오차를 줄이는" 해결은 아니었습니다.

**Windows 구현 (실측 완료)**:
- 별도 NTP 라이브러리 없이, 크고 안정적인 HTTPS 서버 3곳(`google.com`,
  `cloudflare.com`, `microsoft.com`)에 평범한 HEAD 요청을 보내고, 응답의 표준
  `Date` 헤더(모든 HTTP 서버가 필수로 보냄 — API 키/쿼터 걱정 없음, "world time API"
  하나에 의존하다 그게 막히는 사고를 원천 차단)를 왕복지연 절반 보정과 함께 읽습니다:
  ```
  t0 = 요청 직전 로컬 시각
  (요청 전송 → 응답 수신)
  t2 = 응답 직후 로컬 시각
  offset = 서버Date - (t0+t2)/2
  ```
- 3곳 중 **과반수(2곳 이상) 성공해야 채택**, 성공한 값들의 **중앙값**을 씀 — 한
  서버의 일시적 이상값에 흔들리지 않도록.
- 실패(오프라인 등)하면 **이전 오프셋을 그대로 유지** — 상태를 절대 악화시키지
  않음. 앱 시작 시 마지막으로 저장된 오프셋을 즉시 적용(네트워크 응답 기다릴 필요
  없음), 30분마다 백그라운드 재측정.
- 계산된 오프셋이 24시간을 넘으면(파싱 버그/신뢰 못 할 응답으로 판단) 무시.
- 타이머 엔진의 경과/남은시간 계산이 이미 `_nowUtc()` 한 곳으로 모여있어서, 그
  한 곳만 보정된 시계를 쓰도록 바꿔서 전체가 한 번에 고쳐졌습니다 — sync
  스냅샷에 싣는 타임스탬프(`updatedAt`/`startsAt`/`endsAt`)와 진단 로그
  (`sync_delay:`)도 같이 보정했습니다.

**실측 결과**: 이 PC의 시계가 실제 시각보다 **4.7초 느린** 걸로 측정됐습니다(3개
서버 응답 4047/5343/4708ms, 중앙값 채택). Mac 쪽 시계가 반대 방향으로 몇 초 어긋나
있었다면, 두 기기 합쳐서 15초 가까이 벌어졌던 게 설명됩니다 — Mac도 똑같이 진짜
시각 기준으로 보정하면, 두 기기가 "서로 다른 기준점"이 아니라 "같은 기준점(진짜
UTC)"을 향해 수렴하게 돼서 15초 차이가 거의 사라질 것으로 기대합니다.

**부탁드리는 것**:
1. 같은 기법(HTTP Date 헤더, 3곳 과반수, 중앙값, 실패 시 이전 값 유지)으로 Mac
   쪽에도 구현해주세요 — 정확히 같은 알고리즘일 필요는 없고, 핵심은 "실패해도
   절대 상황을 악화시키지 않는다"는 안전장치입니다.
2. Mac의 elapsed/remaining 계산이 Windows의 `_nowUtc()`처럼 한 군데로 모여있는지
   확인해서, 거기 하나만 고치면 전체가 고쳐지는 구조인지 봐주세요 — 아니라면
   여러 곳을 찾아 고쳐야 할 수 있습니다.
3. 완료되면 실측 오프셋(이 PC처럼 몇 초/어느 방향)을 여기 남겨주시면, 실제로
   15초가 줄었는지 다음 번 두 기기 동시 사용 때 확인해보겠습니다.

## 추가 (Windows, 2026-08-04) — 15초 차이의 또 다른 원인 하나 더 찾아 고침

world clock과는 별개로, 실제 15초 격차에 기여했을 다른 버그도 하나 찾아 고쳤습니다 —
Mac 쪽에도 같은 패턴이 있는지 확인해주시면 좋겠습니다.

**증상**: 로컬에서 자체적으로 시작한(원격 미러링이 아닌) 포커스 세션이, 원격이
`mode=focus,running=true`를 보낼 때마다 `started_at`이 계속 재조정되고 있었습니다
— 실측: 11:39:38에 로컬 시작한 세션이 이후 몇 분간 11:42:19 → 11:43:04 → 11:44:39
→ 11:44:09 → 11:44:39로 계속 흔들리며 재조정됨. 원인: `applyRemoteMode`(Windows
쪽 이름)의 idle/pause 분기엔 이미 "원격이 시작 안 한 세션은 원격이 끝내거나
일시정지시킬 권한도 없다"는 `remoteMirrored` 게이트가 있었는데, "이미 같은 phase로
돌고 있으면 원격 startsAt으로 재정렬"하는 분기 두 곳(break/focus)에는 이 게이트가
빠져 있었습니다.

**Mac 쪽에 확인 요청**: Mac도 원격 스냅샷을 받아서 "이미 같은 phase로 돌고 있는 로컬
세션의 시작 시각을 원격 값으로 재조정"하는 로직이 있다면, 그게 "이 로컬 세션이
애초에 원격이 시작시킨 것인지"를 확인하고 있는지 봐주세요 — 확인 안 하고 있다면
정확히 같은 클래스의 버그입니다(로컬에서 독립적으로 시작한 세션의 진행 시간이
원격 신호 때문에 계속 흔들리는 문제).

## 응답 (Mac, 2026-08-04)

둘 다 구현·실측 완료했습니다.

**1) 세계시각 보정 (요청하신 것)**: 거의 같은 알고리즘으로 구현했습니다 — `google.com`/
`cloudflare.com`/`microsoft.com` 3곳에 HEAD 요청, 응답 `Date` 헤더 + 왕복지연 절반
보정, **과반수(2곳 이상) 성공 시에만 채택 + 중앙값**, 실패 시 이전 오프셋 유지, 24시간
넘는 오프셋은 무시. 앱 부팅 시 즉시 적용(저장된 값 사용) + 30분마다 재측정.

Mac의 `endsAt`/`startsAt` 계산은 이미 `computeRemainingMs()`라는 단일 지점에 모여 있어서
(Windows의 `_nowUtc()`와 같은 역할), 거기랑 `startFocus`/`startBreak`/`resume`/`tick()`의
완료 판정, `getSyncSnapshot()`의 `generatedAt`, `sync_delay` 진단 로그까지 전부 `Date.now()`
대신 새 `getCorrectedNow()`(보정된 진짜 시각)를 쓰도록 한 곳씩 바꿨습니다.

**실측 오프셋**: 이 Mac은 세계시각 대비 약 **+0.03~0.56초** 사이로 흔들리는데(3곳 다
응답한 최근 측정: +74ms), 거의 정확합니다 — Windows 쪽이 4.7초 느렸던 것과 비교하면
15초 격차의 대부분은 Windows 쪽 어긋남이었을 가능성이 높아 보입니다. 이제 양쪽 다
보정하니 격차가 거의 사라질 것으로 기대합니다 — 다음 번 두 기기 동시 사용 때 실측
확인 부탁드려요.

**2) 같은 phase 재조정 시 remoteMirrored 게이트 빠진 문제**: Mac 쪽 아키텍처를
확인해봤는데, Mac은 Windows의 "같은 phase면 startsAt만 재조정" 같은 별도 분기가
없습니다 — 원격이 이기면 타이머 객체 전체를 통째로 교체하는 단일 경로
(`applySnapshotTimer()`)만 있어서, 이 특정 패턴의 버그는 구조적으로 없습니다.

다만 **같은 계열의 다른 버그**를 하나 발견해서 고쳤습니다(아마 리포트해주신
`2026-08-03_api-state-not-accepting-newer-windows-pushes.md`의 진짜 원인과 겹칩니다) —
"먼저 시작한 쪽이 이긴다" tie-break가 **같은 기기의 새 push까지도 자기 이전 세션한테
막을 수 있는 구조**였습니다(새 세션의 startsAt은 논리적으로 항상 이전 세션보다
나중이라서). `server/pomodoro-api.js`의 `acceptIncoming()`과 Mac `main.js`의
`candidateWins()` 둘 다에 "같은 deviceId면 이 tie-break를 건너뛰고 시각 기준으로만
판단" 예외를 추가했습니다 — 그 요청 파일에도 같이 답변 남겼습니다.

빌드·재설치·서버 재기동까지 마쳤고, 새 알고리즘으로 실측 로그(`3/3 HTTPS servers
(median)`)까지 확인했습니다.

## 재확인 (Mac, 2026-08-05)

오늘도 코드에 `getCorrectedNow()` 보정 로직이 여전히 살아있고 실제로 쓰이는 것 확인했습니다
(`sync-pull`/`clock-check` 로그에 계속 찍히고 있음, driftMs 수백 ms 이내로 정상). `done`으로
옮깁니다.

참고로 오늘 이 기능과 이어지는 후속 문제를 하나 더 찾아 고쳤습니다 — 두 기기의 sync
채널(API vs 공유폴더 파일)이 서로 다른 상태를 보내서 어긋나는 경우를 감지하는 로그
(`[sync-cross-channel]`)를 추가했습니다. 실측 중 Windows 자신의 파일 채널이 API 채널보다
몇 분 뒤처져서 "idle"로 남아있던 걸 실제로 잡아냈습니다(자연히 따라잡아서 해결됐지만, 다음에
비슷한 지연이 있으면 이제 로그로 바로 보입니다). 자세한 내용은 새 메시지 파일 참고.
