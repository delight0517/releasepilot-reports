# 적응형 발견 인터뷰 방식 (Adaptive Discovery Interview) — 2026-08-19 고정

`growth_tree_counseling_protocol.md`가 "언제 상담을 시작하는가"를 정한다면, 이 문서는
**상담이 시작된 뒤 실제로 어떻게 질문하고 종합하는가**를 정한다. yena_career 상담
(2026-08-19, 예나 페르소나)에서 실제로 효과가 있었던 방식을 일반화한 것 — 나중에 이 자체를
앱 기능(질문 엔진)으로 옮길 수 있도록 사람이 손으로 하던 판단을 구조로 적어둔다.

## 왜 고정 문서화하는가

사용자 지적(2026-08-19): "질문과 답변을 보면서 효과적인지를 보고, 나중에 앱으로 만들 때
쓸 수 있도록 프로토콜을 고정화해달라." 즉 이 방식 자체가 재사용 가능한 자산이어야 한다 —
이번 상담이 잘 됐다고 끝나는 게 아니라, 다음에 다른 사람/다른 트리에도, 또는 실제 앱
UI로 옮겨도 같은 품질이 나오게.

## 핵심 원칙 (실제로 이번 상담에서 검증된 것)

1. **첫 질문은 넓게, 답을 보고서야 다음 질문을 만든다.** 처음부터 20개 질문을 한꺼번에
   쏟아붓지 않는다 — "왜 안 했어요?" 같은 열린 질문 하나로 시작해서, 그 답에 나온 **키워드
   하나하나**(이번엔 "미디어 만들기")를 다음 라운드에서 세분화해서 다시 묻는다.
2. **답이 이전 전제를 뒤집으면, 그 자리에서 즉시 정정하고 계속 진행한다.** 이번 상담에서
   "강사 Pool이 재미없다"는 처음 답이 2라운드 후 "강사/강의는 좋다, 다만 기관 경유 방식이
   싫을 뿐"으로 정정됐다. 이걸 무시하고 원래 가설로 계속 밀어붙이면 안 된다 — 정정을
   발견 로그에 "정정됨"으로 명시하고, 그 다음 질문부터 새 이해를 기준으로 짠다.
3. **최소 2라운드는 캐묻는다, 첫 답 하나로 옵션 메뉴로 넘어가지 않는다.** 목표 라운드 수를
   미리 정하지 않는다 — "이제 더 이상 새로운 정보나 모순이 안 나온다"는 신호(같은 내용의
   답이 반복되거나, 답변자가 스스로 "이게 답인 것 같아" 식으로 정리하기 시작함)가 올 때까지.
4. **라운드마다 여러 각도에서 동시에 묻는다(한 번에 한 질문씩 핑퐁하지 않는다).** 이번
   상담의 2라운드는 "3D 세계의 형태/연재 위치/기존 스킬/이미 구상해둔 것"과 "알바 종류/생계
   압박" 두 축을 한 번에 물었다 — 답변자가 한 번에 답하고 싶은 만큼 답하게 하고, 답 안 된
   항목만 다음 라운드에서 다시 좁혀 묻는다.
5. **종합(synthesis) 전에 절대 결론(옵션 메뉴)로 건너뛰지 않는다.** 캐묻기가 끝나면 —
   (a) 지금까지 들은 걸 요약해서 반사(reflect back)한다("정리하면 이런 거죠?"), (b) 그
   요약이 맞는지 확인받는다, (c) 그러고 나서야 방향 옵션을 제시한다. 요약 없이 바로
   "그럼 A/B/C 중 뭐로 할까요"로 가면 answered-but-not-understood가 된다.
6. **저항/회피 신호가 나오면 병리화하지 않고 그대로 반사만 한다.** 이번 상담에서 "능력은
   있는데 일하고 싶지 않다"는 답이 나왔을 때, 진단하거나 원인을 단정하지 않고 "이 패턴이
   다른 것과 같은 뿌리일 수도 있겠다" 정도로만 남기고 본인에게 다룰지 물어볼 대상으로
   남겨둔다 — AI 상담 페르소나가 넘지 말아야 할 선.
7. **구조적 변경(트리 재설계 등)은 종합 후 "초안 제안"으로만 내놓고, 실제 반영은 항상
   별도 명시적 동의 후.** 종합 단계에서 "이렇게 재구성해볼 수 있을 것 같은데 어때요?"까지는
   상담의 일부지만, 실제 파일 수정은 그 확인을 받은 다음 턴에서.

## 데이터 모델 (앱으로 옮길 때 이 구조를 그대로 쓸 것)

```json
{
  "sessionId": "yena_career-2026-08-19-01",
  "personSlug": "yena_career",
  "trigger": "user_initiated | scheduled_stall_checkin",
  "rounds": [
    {
      "round": 1,
      "askedBy": "예나",
      "questions": ["열린 질문 텍스트..."],
      "answers": ["원문 답변..."],
      "extracted": [
        {"tag": "reason_given", "value": "미디어 만드는 거에 관심 생김", "confidence": "raw"}
      ]
    },
    {
      "round": 2,
      "questions": ["1라운드 답의 키워드를 좁힌 세부 질문들..."],
      "answers": ["..."],
      "extracted": [
        {"tag": "media_interest_detail", "value": "3D 세계+연재, 웹툰형", "confidence": "confirmed"},
        {"tag": "instructor_pool_feeling", "value": "재미없음", "confidence": "raw", "status": "corrected_in_next_round"}
      ]
    },
    {
      "round": 3,
      "questions": ["..."],
      "answers": ["..."],
      "extracted": [
        {"tag": "instructor_pool_feeling", "value": "강의 자체는 좋음, 기관 경유 방식만 싫음", "confidence": "confirmed", "corrects": "round2:instructor_pool_feeling"},
        {"tag": "resistance_pattern", "value": "능력 있으나 흥미 없는 노동 전반에 저항감, 금전 압박 아님", "confidence": "confirmed"}
      ]
    }
  ],
  "readyForSynthesis": true,
  "synthesis": "사용자에게 반사한 요약 텍스트",
  "synthesisConfirmed": null,
  "proposedDirections": ["draft option A", "draft option B"],
  "appliedChanges": []
}
```

- `extracted[].confidence`: `raw`(1회 언급, 미확인) → `confirmed`(후속 라운드에서 재확인/구체화됨) →
  이전 라운드 값을 뒤집으면 `corrects` 필드로 어떤 걸 정정하는지 명시(삭제하지 않고
  이력을 남긴다 — 나중에 "저 사람이 원래 이랬다가 이렇게 바뀌었구나"를 볼 수 있어야 함).
- `readyForSynthesis`: 최근 라운드에 `raw`인 채 안 좁혀진 태그가 없고, 새 태그도 안 나오면
  true — 이때 종합 단계로 넘어간다(질문 엔진이라면 이 조건으로 "더 물을지 종합할지" 분기).
- 앱으로 만들 때는 이 JSON을 그대로 세션 로그로 쓰고, `counseling_log.md`류 사람이 읽는
  마크다운은 이 구조에서 자동 생성하는 뷰로 취급하면 된다(지금은 사람이 직접 마크다운으로
  쓰고 있지만, 스키마가 같으니 나중에 뒤집기 쉬움).

## 지금 수동으로 하고 있는 것 vs 앱이 되면 달라질 것

- 지금: Claude 세션이 매 라운드 질문을 즉석에서 만들고, `counseling_log.md`에 사람이 읽는
  형태로 직접 기록.
- 앱이 되면: 위 JSON 구조를 실제 상태로 저장하고, 질문 생성은 여전히 LLM이 하되(고정된
  질문지가 아니라 "이전 답의 raw 태그를 좁히는 질문 생성" 같은 지침으로), `synthesis`
  단계에서 사람 확인(버튼/답변)을 받는 UI가 붙는다. **질문을 미리 다 정해두는 방식으로
  가면 안 된다** — 이번 상담이 효과적이었던 이유가 정확히 "이전 답을 보고 다음 질문을
  만든 것"이기 때문에, 앱이 되어도 이 적응형 생성 방식은 유지해야 한다.
