## 0. 가장 먼저 말해야 할 것 — 세 사이트가 "구직"이라는 목적으로 안 묶여 있다

세 사이트를 순서대로 읽으면서 계속 걸린 문제: **`about/`은 자기소개서라기보다 브랜드 선언문이고, `portfolio/`는 개발과 무관한 창작 아카이브이고, 실제 "고용해달라"는 메시지를 담은 건 `dev-portfolio/` 하나뿐**이다. 그런데 `about/`의 1차 CTA 버튼이 `dev-portfolio/`가 아니라 리포트 허브(`index.html`, 개발 도구 카탈로그)로 연결돼 있다 — 이건 채용 담당자를 정확히 필요한 곳의 반대 방향으로 보내는 버그에 가깝다. 아래 개별 항목보다 이걸 1순위로 본다.

## 1. `about/index.html` — 김근후 · VIVID 소개 페이지

### (1) 구조/정보구조
현재 순서: 브랜드마크 → 히어로+CTA → **세계관(문학 이론 표)** → 페르소나 5인(본인 3 + AI 페르소나 5) → 사진 미리보기 → 연락처 → 브런치 글 → 기타 링크.

채용 담당자가 몇 초 안에 "이 사람이 무슨 일을 하고 왜 뽑을 만한가"를 알 수 있어야 하는데, 지금은 **기술 스택·경력·프로젝트 언급이 히어로 바로 아래가 아니라 "세계관" 섹션(루터·융·C.S.루이스 인용, 브런치 글 구조 분석표) 뒤에야** 나온다. 개발자 채용 관점에서 이 순서는 위험하다 — 문학/신학 에세이 분석을 먼저 읽고, 그다음에야 "개발자 — 4VPN Blocker, 35Closer Timer" 한 문단을 만난다.

**Before**: `#worldview`(문학 이론) 섹션이 히어로 바로 다음.
**After 제안**: 히어로 바로 아래에 "한눈 요약" 스트립을 새로 추가 — 직함/기술스택 배지 4~6개 + "만든 것 3개" 미니 카드(4VPN Blocker · 35Closer Timer · 사계기록) + dev-portfolio 링크. `#worldview`는 그 아래로 유지(개성을 보여주는 섹션 자체는 살린다 — 삭제 제안 아님, **순서만** 바꾸는 것).

```html
<!-- 히어로 바로 아래, #worldview 앞에 삽입 -->
<section id="quicklook" style="margin-top:32px;">
  <div class="stack-row" style="display:flex;flex-wrap:wrap;gap:8px;justify-content:center;">
    <span class="stack-chip">Flutter/Dart</span>
    <span class="stack-chip">Swift/SwiftUI</span>
    <span class="stack-chip">Electron</span>
    <span class="stack-chip">Claude API 연동</span>
  </div>
  <p class="lede" style="text-align:center;margin-top:14px;">
    자기통제 앱 2개를 실기기까지 출시 준비 중 —
    <a href="../dev-portfolio/" style="color:var(--seal-ink);">개발 포트폴리오 전체 보기 →</a>
  </p>
</section>
```
(`.stack-chip` 클래스는 `dev-portfolio/index.html`에 이미 있는 걸 그대로 재사용하면 톤 일치됨.)

### (2) 색상/비주얼
파치먼트(양피지)+잉크+인장 팔레트는 일관성 있고 다크모드까지 짝을 맞춰 만들어져 있다 — 이 자체는 잘 만들었다. 다만 **`--ink-faint: #8a7c56`가 `--paper: #f6efdb` 위에서 쓰이는 곳(코드 좌표 nav 10.5px, `.post .meta` 10px)은 대비가 낮다.** 실측은 못 했지만 옅은 베이지 위 옅은 카키 조합은 WCAG AA(4.5:1) 근처거나 미달일 가능성이 높다 — 작은 폰트라 더 위험.

**After 제안**: `--ink-faint`를 다크 방향으로 살짝 내리거나(`#7a6c48` 정도), 10px 이하로 쓰는 곳(`.post .meta`, `nav.coords`)만 `--ink-dim`으로 상향. 브라우저 개발자도구로 실측 후 최종값 확정 필요 — 이건 다음 세션에서 실측하고 반영하는 걸 권장.

파치먼트 컨셉 자체는 "개성" 점수에서는 강점이지만, **전통적인 IT/스타트업 채용 담당자에게는 "지도 제작자" 컨셉이 개발 역량과 무관하게 읽힐 위험**이 있다 — 이건 색상 문제가 아니라 아래 (5) 개성 항목에서 다룸.

### (3) 이해도
- 기술 스택이 텍스트 문단(`"4VPN Blocker, 35Closer Timer는..."`) 안에 묻혀 있어 스킴하기 어렵다. → (1)에서 제안한 배지형 요약으로 해결.
- 경력/학력 타임라인이 전혀 없다. "홍익대 게임그래픽학과"가 페르소나 카드 안에 한 줄로만 존재(line 294) — 학력을 찾으려면 5개 페르소나 카드를 다 읽어야 발견됨.
- 연락처 섹션(`#contact`)은 전화/이메일만 있고 **이력서 링크가 없다.**

**After 제안**: `#contact` 섹션에 이력서(PDF 또는 노션) 링크 카드 1개 추가. 이력서가 아직 없다면 이번 기획안에서 "만들 것" 항목으로만 남기고 코드는 넣지 않는다(없는 파일을 링크하면 404).

### (4) 직관성
- 상단 nav(`nav.coords`)의 "포트폴리오" 링크는 `dev-portfolio/`로 정확히 감 — 이건 잘 됨.
- 문제는 **히어로의 1차 CTA 버튼**("만든 것 보기 →")이 nav와 다른 목적지(리포트 허브 루트)로 감. 첫 화면에서 가장 눈에 띄는 버튼이 스킬트리·앱 진행률판·요청 채널 같은 내부 운영 콘텐츠로 채용 담당자를 데려간다 — nav의 "포트폴리오"와 목적지가 다르다는 것 자체가 혼란을 만든다.

**Before**:
```html
<a class="cta" href="https://delight0517.github.io/releasepilot-reports/" target="_blank" rel="noopener">
  만든 것 보기 →
</a>
```
**After**:
```html
<a class="cta" href="../dev-portfolio/" target="_blank" rel="noopener">
  만든 것 보기 →
</a>
```
(루트 허브로 가고 싶다면 별도의, 덜 강조된 링크로 `#elsewhere`나 footer에 남기는 걸 권장 — 1차 CTA 자리는 채용 목적에 직접 연결된 곳이어야 함.)

### (5) 개성
가장 강점인 부분. "마음의 지도 제작자"라는 컨셉, AI 페르소나 팀(차실장/클로이 박/박새로이/차차차/예나) 세계관, 등고선 텍스처, 인장 색 — 어디서도 본 적 없는 조합이고 일관되게 실행돼 있다. 이건 **삭제하거나 축소하자는 게 아니라, 위치를 조정하자는 제안**이다. 지금처럼 히어로 바로 뒤에 나오면 "이 사람 뭐하는 사람이지?"를 채용 담당자가 답 못 한 채로 개성을 먼저 만나게 된다. (1)에서 제안한 "한눈 요약"을 앞에 놓고 세계관/페르소나는 그 뒤에 그대로 두면, 개성은 유지하면서 "먼저 신뢰를 얻고 나서 매력을 보여주는" 순서가 된다.

## 2. `dev-portfolio/index.html` — 앱 개발 포트폴리오

이 페이지는 세 사이트 중 **구직 목적에 가장 맞게 이미 설계돼 있다** — 히어로 아래 기술스택 칩, 라이브 데모, 케이스 스터디, 그리고 이미 자체적으로 "클로이 박 체크" 섹션(2026-08-10 작성)이 박혀서 갭을 스스로 추적하고 있다. 이번 라운드에서 그 체크리스트를 다시 읽어봤는데 **6개 항목 중 하나도 해결되지 않은 상태**다. 이번 기획안은 새 문제보다, 이미 진단된 것 중 채용 확률에 가장 직접적인 영향을 주는 걸 우선순위로 다시 정리하는 데 집중했다.

### (1) 구조/정보구조
히어로 → 검색/필터 → 라이브 데모 → 케이스 스터디 → 자체 체크리스트 순서는 합리적이다. 다만 **연락처/이력서 섹션이 아예 없다** — `about/`에는 있는 전화/이메일 링크가 정작 채용 목적이 가장 강한 이 페이지엔 없다. 방문자가 프로젝트를 다 훑고 "연락하고 싶다"는 마음이 들어도 다음 행동으로 이어질 곳이 없다(2026-08-10 체크리스트 5번 항목과 동일 — 아직 미해결).

**After 제안**: `.chloe` 섹션과 `footer` 사이에 `about/`의 `.links` 패턴을 재사용한 연락처 블록 추가.
```html
<div class="section-head" style="margin-top:40px;"><h2>연락</h2></div>
<div class="demo-row" style="flex-direction:row;flex-wrap:wrap;">
  <a class="demo-card" href="mailto:delight0517@hongik.ac.kr" style="flex:1;min-width:220px;">
    <span class="demo-glyph">✉️</span>
    <span><span class="demo-name">이메일로 연락</span>
      <span class="demo-desc">delight0517@hongik.ac.kr</span></span>
  </a>
</div>
```

### (2) 색상/비주얼
크림+앰버 팔레트, `--good`/`--warn`/`--live` 상태색까지 목적별로 분리돼 있어 일관되고 읽기 편하다. 대비도 무난 — `--ink-dim: #6b6a5f` on `--card: #ffffff`는 계산상 AA를 통과한다(약 5.4:1). 이 페이지 색상은 손댈 게 없다.

### (3) 이해도
- 상단 기술스택 칩(Flutter/Swift/Electron/Firebase/Claude API 등)은 3초 안에 "이 사람이 뭘 쓰는지" 답을 준다 — 잘 됨.
- 다만 **케이스 카드의 `case-stage` 배지가 진행률 데이터를 그대로 노출**한다(`앱 등록`, `코드 분석`, `타겟·수요 검증` 등). 이건 내부 트래킹 도구(`progress/`)엔 유용하지만, 채용 담당자 눈엔 "아직 스토어 제출도 안 한 프로젝트"로 읽혀 완성도가 낮아 보이는 역효과가 날 수 있다.

**After 제안**: `case-stage` 배지를 구직용 문구로 치환하는 별도 매핑 추가(내부 트래킹 값은 그대로 두고, 표시 라벨만 구직 관점으로 재해석) — 예: `mvp_locked` 이전 단계는 "설계·개발 중"으로, `submitted` 이후만 실제 스토어 단계명 노출. 완전히 숨기자는 게 아니라 **채용 담당자에게 의미 있는 해상도로 뭉뚱그리자**는 제안.

### (4) 직관성
검색창(`/` 단축키), 태그 필터, 클릭 가능한 스택 태그 — 조합이 자연스럽고 실제로 잘 작동한다. `back-link`가 `position: fixed`인데 모바일에서 히어로 텍스트와 겹치는지는 실기기 확인이 필요 — 코드만으로는 z-index 충돌 가능성은 낮아 보이나(z-index:5, 히어로는 배경색 위 텍스트뿐) 실사용 스크린샷으로 한 번 확인 권장.

### (5) 개성
자체 비평 섹션(`.chloe`)이 살아있는 코드 자체 안에서 "지금 이 포트폴리오, 채용 관점에서 어디가 비는지"를 정직하게 드러낸다는 게 오히려 개성이자 신뢰 신호다 — 이건 잘 만든 부분이니 유지 권장. 다만 이번 리뷰에서 발견: **`case-tag`나 케이스 카드 자체의 시각적 개성(아이콘)은 아직 약하다** — `hasIcon: true`인 4개 프로젝트가 실제로는 `assets/icons/*.png` 파일 존재 여부를 확인 못 했다(이 세션에서 파일 리스트까지는 확인 안 함, 다음 라운드에서 실제로 로드되는지 스크린샷 확인 필요).

## 3. `portfolio/index.html` — 사진·3D·영상·웹툰·글

### (1) 구조/정보구조
매체 탭(사진/3D/영상/웹툰/글) 구조 자체는 훌륭하지만, **이 페이지 전체에 "이 사람이 개발자로서 지원 중"이라는 맥락이 전혀 없다.** 히어로에 이름도, 직함도, dev-portfolio로의 링크도 없다 — footer에 "리포트 허브로 돌아가기"만 있다. 채용 담당자가 (예를 들어 이력서의 링크를 타고) 이 페이지에 먼저 도달하면, 개발 역량을 확인할 방법이 전혀 없이 사진/웹툰 아카이브만 보게 된다.

**After 제안**: 히어로 `<p class="native-note">` 아래에 한 줄만 추가.
```html
<p class="native-note" style="margin-top:8px;">
  개발 프로젝트는 <a href="../dev-portfolio/" style="color:var(--accent-ink);">개발 포트폴리오 →</a>에 따로 정리돼 있습니다.
</p>
```
비용 대비 효과가 가장 큰 한 줄 변경 — 코드 변경량은 최소, 회수하는 "길 잃은 방문자" 수는 클 것으로 예상.

### (2) 색상/비주얼
매체별 액센트 색 분리(사진=safelight red, 3D=시안, 영상=앰버, 웹툰=바이올렛, 글=중성) — 코드 주석에도 참고 사이트까지 명시돼 있을 만큼 의도가 분명하고 실행도 일관됨. 이건 세 사이트 중 가장 "의도적으로 디자인됐다"는 인상을 준다. 손댈 게 없다.

### (3) 이해도 / (4) 직관성
탭+뷰모드(격자/스토리) 전환, 3D `<model-viewer>` 드래그 회전, 웹툰 세로 리더, 유튜브 lightbox — 기능적으로 잘 만들어져 있고 직관적이다. 문제는 이해도 쪽인데, **"이걸 왜 보고 있는지"에 대한 맥락이 없어서** 기능이 아무리 좋아도 구직 목적에서는 효과가 반감된다. (1) 항목과 동일한 문제의 다른 표현.

### (5) 개성
세 사이트 중 가장 개성이 강하다 — Three.js 없이 `<model-viewer>`로 실용적 절충을 택한 판단, 필름 릴/컨택트시트 은유, 매체별 색 분리까지 완결도가 높다. 다만 구직 맥락에서는 **"개발자 지원자"보다 "종합 크리에이터"로 각인시킬 위험**이 있다 — 지원 직군이 순수 개발직이라면 이 페이지는 부차적 링크로 위치시키고, dev-portfolio를 가장 눈에 띄는 대표작으로 두는 정보 위계가 필요하다. (이건 코드 변경 제안이 아니라, 사용자가 어떤 직군에 지원하는지에 따라 우선순위 재확인이 필요한 지점 — 확인 필요 항목으로 남김.)
