# 클로이 박 — UX 개선 기획안 2026-08-31

**대상**: `about/`, `dev-portfolio/`, `portfolio/` (+ 연결 관계상 `game-artist/` 참고)
**목표**: 이 세 페이지가 실제로 취업 확률을 올리는가 — "몇 초 안에 이 사람이 뭘 하는 사람이고
왜 뽑을 만한지"가 전달되는지를 기준으로만 평가함. 디자인 자체의 미학은 부차적.
**상태**: 제안만 함. 구현은 사용자 승인 후 별도 세션에서.

## 0. 시스템 전체를 먼저 봐야 하는 이유

세 페이지를 개별적으로 보기 전에, 채용 담당자 입장에서 "이 사람 포트폴리오가 총 몇 개고
어디부터 봐야 하는지"부터 확인했다. 실제로 뒤져보니 **포트폴리오 성격의 페이지가 4개**다:

- `about/` — 본인 소개 허브 (개발자+작가+비주얼+AI팀장 정체성 통합)
- `dev-portfolio/` — 앱 개발 케이스 스터디 (채용 목적 명시)
- `portfolio/` — 사진·3D·영상·웹툰·글 아카이브
- `game-artist/` — "김근후 — 3D 게임 아티스트 · 홍익대 게임그래픽" (완전히 별도 페이지, ArtStation 커버 이미지까지 갖춘 완성도 있는 사이트)

문제: **`about/`의 내비게이션 어디에도 `game-artist/`로 가는 내부 링크가 없다.** `about/`에는
"ArtStation" 외부 링크(`artstation.com/kaito_ren`)만 걸려 있고, 이 저장소 안에 이미 만들어둔
`game-artist/`라는 자체 완성 페이지는 존재 자체가 드러나지 않는다. 게임 그래픽 관련 채용
담당자가 `about/`을 통해 들어오면 이 사람이 3D 게임 아티스트 포트폴리오를 따로 갖고 있다는
걸 영영 모르고 나갈 수 있다.

**제안**: `about/`의 `nav.coords`와 "PERSONAS" 섹션의 비주얼 담당(🎮 홍익대 게임그래픽학과) 항목에
`game-artist/`로의 내부 링크를 추가한다.

```diff

    <a href="#worldview">세계관</a>
    <a href="#work">하는 일</a>
    <a href="../dev-portfolio/">포트폴리오</a>
+   <a href="../game-artist/">3D 아트</a>
    <a href="../stage/">무대</a>
    ...
```

```diff
        <div class="glyph">🎮</div>
        <div>
          <h3>비주얼 — 홍익대 게임그래픽학과, 필명 "Kaito Ren"</h3>

+         <p>ArtStation에 게임 비주얼 작업을 올린다. 코덱스: 죄악, 네온 듄: 사막 기억 창조자.
```

## 1. `about/` — 본인 소개 허브

### (1) 구조/정보 구조
현재 순서: 브랜드마크 → 히어로(이름+한 줄 카피+CTA) → 세계관(문학적 사고 엔진 표) →
페르소나(개발자/작가/비주얼 + AI팀) → 사진 미리보기 → 연락처 → 글 → 링크.

**문제**: 히어로의 CTA `"만든 것 보기 →"`가 `dev-portfolio/`가 아니라 **저장소 루트
(`releasepilot-reports/` 리포트 허브 전체)로 연결**된다. 루트에는 growth 트리, ops-calendar,
requests, 온갖 실험 리포트가 뒤섞여 있다 — 채용 담당자가 "만든 것"을 누르면 정리된 개발
포트폴리오가 아니라 개인 운영 대시보드 전체를 보게 된다. 클릭 한 번으로 가장 정돈된 자료
대신 가장 안 정돈된 자료로 보낸다는 게 이 사이트에서 가장 손해 큰 실수다.

**Before/After**:
```diff
-   <a class="cta" href="https://delight0517.github.io/releasepilot-reports/" target="_blank" rel="noopener">
-     만든 것 보기 →
-   </a>
+   <a class="cta" href="../dev-portfolio/">
+     개발 포트폴리오 보기 →
+   </a>
```
(내부 상대경로로 바꾸면 `target="_blank"`도 뗄 수 있다 — 같은 사이트 안 이동인데 새 탭을 여는
건 불필요한 마찰이다.)

### (2) 색상/비주얼
파치먼트(양피지)+잉크+인장 팔레트는 다크모드까지 `prefers-color-scheme`와 `data-theme` 양쪽을
정확히 처리해뒀고(`about/index.html:37-50`), 대비도 무난하다. **이 세 페이지 중 가장 잘 만든
디자인 시스템**이다 — 손댈 필요 없음.

### (3) 이해도
히어로에 **직함이 없다**. `kicker`("VIVID · 근성장 · Rogan Kim") → `h1`("김근후") → `sub`
("마음의 지도를 그리는 사람")까지 다 읽어도 "이 사람이 개발자다"라는 사실이 안 나온다.
개발자를 채용하러 온 담당자가 3초 안에 확인하고 싶은 건 시(詩)적 정체성이 아니라 역할이다.
"세계관" 섹션(루터/융/C.S.루이스 인용 구조 분석)은 개성 면에서는 훌륭하지만, 채용 목적
스캔 우선순위에서는 "하는 일" 섹션보다 먼저 나올 이유가 없다.

**Before/After** (히어로에 역할 한 줄 추가):
```diff
    <p class="kicker">VIVID · 근성장 · Rogan Kim</p>
    <h1>김근후</h1>
+   <p style="font-family:var(--mono);font-size:12px;color:var(--ink-dim);margin:0 0 8px;">
+     앱 개발자 (Flutter · Swift) · 개인 프로젝트 7개 기획~배포
+   </p>
    <p class="sub">마음의 지도를 그리는 사람</p>
```

### (4) 직관성
앵커 내비게이션(`nav.coords`)은 짧고 명확해서 좋다. 다만 위 0번에서 지적한 대로
`game-artist/`가 빠져 있는 게 유일한 구멍.

### (5) 개성
멀티 페르소나(AI 팀 5명 — 차실장/클로이 박/박새로이/차차차/예나) 소개는 이 사람만의
확실한 차별점이다. 다만 지금은 "이 사람이 만든 걸 의인화한 재미있는 서사"로만 읽히기
쉽다. 실제로는 **Claude Code 기반 멀티에이전트 오케스트레이션을 설계·운영 중이라는
기술적 사실**이고, 이게 개발자 채용 관점에서는 서사보다 훨씬 강한 증거다.

**Before/After** (PERSONAS 섹션 상단에 한 문장 추가):
```diff
    <p class="section-label" style="margin-top:28px;">VIVID 팀 — AI 페르소나</p>
+   <p class="lede" style="margin-top:-4px;">역할별로 분리된 5개의 Claude Code 에이전트를
+   직접 설계·운영하며, 각자 다른 페르소나로 서로 다른 업무(디자인 검토/디버깅/SEO/데이터)를
+   독립적으로 처리하게 만들었다 — 아래는 그 팀의 실제 소개.</p>
    <div class="personas">
```

## 2. `dev-portfolio/` — 앱 개발 케이스 스터디

### (1) 구조/정보 구조
히어로 → 스택 칩 → 검색/필터 → "지금 써볼 수 있는 데모"(라이브 우선) → 프로젝트 케이스 →
클로이 박 자체 체크리스트. **라이브 데모를 케이스 스터디보다 먼저 배치한 순서 자체는
좋은 판단**이다 — 읽기 전에 만져볼 수 있게 하는 게 신뢰를 가장 빨리 만든다.

**문제**: 이 페이지 자체에는 이름/사진/연락처가 전혀 없다. `<a class="back-link">‹
허브로</a>` 하나만 있고, 이 링크도 `about/`이 아니라 저장소 루트로 간다. 채용 담당자가
이 URL을 검색·공유로 바로 열면(허브를 거치지 않고) 이 사람이 누구인지, 어떻게 연락할지
알 방법이 **이 페이지 안에 없다**. 아래 클로이 박 자체 체크리스트에도 이미 "연락처/이력서
링크가 없다"고 스스로 지적해뒀는데(`dev-portfolio/index.html:442`), 이 지적이 나온 뒤로도
여전히 고쳐지지 않은 채 남아 있다 — 이번 리뷰에서 다시 최우선 순위로 올린다.

**Before/After**:
```diff
- <a class="back-link" href="../">‹ 허브로</a>
+ <a class="back-link" href="../about/">‹ 김근후</a>
```
```diff
    <div class="stack-row">
      ...
    </div>
+   <p style="margin-top:18px;font-size:13px;">
+     <a href="mailto:delight0517@hongik.ac.kr" style="color:var(--accent-ink);font-weight:600;">delight0517@hongik.ac.kr</a>
+     · <a href="../about/" style="color:var(--accent-ink);">자기소개 전체 보기 →</a>
+   </p>
```

### (2) 색상/비주얼
크림/앰버 팔레트, 그림자·라운드 코너 일관성 있음, 대비 무난. 다만 `about/`(양피지+인장)와
`portfolio/`(다크룸+세이프라이트 레드)와 나란히 놓고 보면 **세 페이지가 톤이 완전히 달라서
"같은 한 사람의 사이트"라는 신호가 약하다**. 각 페이지 자체 완성도는 높은데, 페이지를
넘나들 때 브랜드 연속성이 끊긴다.

**제안**: 세 페이지 전부를 다시 칠하는 대신, 가장 저비용으로 연속성을 만드는 방법은 상단
back-link/브랜드마크 요소 하나를 통일된 디자인 토큰으로 맞추는 것. 예: 세 페이지 모두
`back-link`를 동일한 위치·폰트(`var(--mono)`, `11px`)로 통일하고 "‹ 김근후"라는 동일 텍스트로
맞추면, 팔레트는 달라도 "탐색 chrome은 하나로 이어져 있다"는 느낌을 준다. (이번 기획안에서는
`dev-portfolio/`만 위에서 이미 반영 예시를 냈고, `portfolio/`도 4번에서 이어서 제안함.)

### (3) 이해도
문제/해결을 `<b>문제</b>`/`<b>해결</b>` 볼드로 명시한 케이스 카드 포맷은 이 세 페이지
중 **채용 관점 이해도가 가장 뛰어난 부분**이다. 실무 판단 근거(예: pmset 로그 파싱,
git-as-DB)까지 한 문장씩 넣어둔 것도 좋음 — 숫자(사용자 수 등) 없이도 기술적 판단력을
보여주는 올바른 전략.

### (4) 직관성
검색+태그 필터는 프로젝트 7개 규모에는 다소 과한 장치다(자체 체크리스트도 이미 인정:
"탐색 기능은 콘텐츠가 없으면 의미가 없다"). 없애기보다는, 스크린샷·GitHub 링크 같은
콘텐츠 공백(아래 5번, 우선순위 목록 참고)을 먼저 채우는 게 순서상 맞다 — 지금 이대로
UI만 남겨둬도 급한 문제는 아님.

케이스 아이콘 문제: `ox-quiz`와 `harugirok`이 아이콘 파일이 동일하다는 지적이
`dev-portfolio/index.html:439`에 이미 있는데, 이번 리뷰 시점에도 그대로다. 채용 담당자가
그리드를 스캔할 때 "어? 이 두 앱이 같은 아이콘이네" 하고 알아채면, 실제로 출시까지 관리가
안 됐다는 신호로 읽힐 위험이 있다 — 최소 하나(우선 harugirok, 실사용 앱이므로)는 교체 필요.

### (5) 개성
`<script type="application/ld+json">`로 Person/SoftwareApplication/BreadcrumbList 구조화
데이터를 심어둔 건(`dev-portfolio/index.html:18-89`) 개인 포트폴리오에서 보기 드문
기술적 완성도다. 다만 이건 화면에 전혀 드러나지 않아서, 사람이 보는 "개성"으로는
전달되지 않는다. 완전히 별개 채널(면접에서 "SEO/AI 검색 노출까지 구조화 데이터로
처리했다"고 말하는 용도)로만 남겨두면 되고, 페이지 자체를 고칠 필요는 없음 — 이 항목은
"손대지 말 것" 쪽 제안.

## 3. `portfolio/` — 사진·3D·영상·웹툰·글 아카이브

이 페이지는 채용 목적이라기보다 개인 창작 아카이브에 가깝다. 다만 게임그래픽 전공자로서
비주얼 역량을 보여주는 보조 자료가 될 수 있어 구조 관점에서만 짚는다.

### (1) 구조/직관성
매체별 탭(사진/3D/영상/웹툰/글) 구조는 깔끔하고, 빈 상태 처리·딥링크(`?tab=`)까지
갖춘 탄탄한 구현이다. 문제는 **히어로에 이름/직함이 전혀 없다는 것**(`<h1>포트폴리오</h1>`
뿐). `about/`을 거치지 않고 이 페이지에 바로 도달한 사람은 "누구의 포트폴리오인지"조차
알 수 없다.

**Before/After**:
```diff
    <span class="eyebrow" id="eyebrow">PORTFOLIO</span>
-   <h1>포트폴리오</h1>
+   <h1>김근후 — 포트폴리오</h1>
    <p class="sub">사진 · 3D · 영상 · 웹툰 · 글 — 매체마다 다른 방식으로 보여줍니다.</p>
```

또한 `footer`의 "← 리포트 허브로 돌아가기" 링크(`portfolio/index.html:344`)도 `about/`이
아니라 저장소 루트로 간다 — `dev-portfolio/`와 같은 패턴의 문제이니 같이 고치는 걸 제안.

### (2)~(5) 색상/이해도/개성
다크룸(safelight red) + 매체별 액센트 컬러 분리 컨셉은 설계 의도가 명확하고(코드 주석에
"참고한 실제 사이트"까지 남겨둔 리서치 기반 결정) 실행도 일관적이다. 손댈 이유 없음.
채용 목적으로는 부차적인 페이지이므로 이번 회차에서 더 깊이 파고들지 않음.
